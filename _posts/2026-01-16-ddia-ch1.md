## Thinking about data systems

Databases, caches, queues are thought of as different categories of tools. They have different access patterns, different performance charactersitics, and very different implementations.

But the line gets blurred:
- **Redis**: a datastore that can also be used as a message queue
- **Kafka**: Message queue with database-like durability guarantees

Moderns applications are usually too complex to solve with a single tool, usually requiring a composite system. In this view, the application developer becomes a **data system designer**, responsible for a composite system that provides specific guarantees to the client.

The book focuses on 3 main concerns for these systems:
1. Reliability: continuing to work correctly when things go wrong.
2. Scalability: Having strategies to handle growth in load
3. Maintainability: Making it easy for people to work on the system over time.

## Reliability

First, distinguish between faults and failures:
- **Fault**: When one component of the system deviates from its specification.
- **Failure**: When the system as a whole stops providing the required service to the user.

It is impossible to reduce the probability of a fault to zero. The goal is to design fault-tolerant mechanisms that prevent the small faults from causing failures.

Types of faults:
1. Hardware faults: hard disks crashing, RAM failing, power outages. This is usually handled with redundancy (RAID or backup generators).
2. Software errors: systematic bugs in the system. These are hard to anticipate and tend to cause more system failures since they are correlated across nodes.
3. Human error: Configuration mistakes by operators, which is the leading cause of outages.
    - Design systems that minimizes the opportunities for error.
    - Sandbox environments to explore and experiment safely using real data.

### Ex. Netflix Chaos Monkey

This is a tool that deliberately kills random server processes in production. The goal is to ensure that the system's fault-tolerance mechanism are actually working. 

## Scalability

Scability isn't a simple "yes" or "no" label. It is talking about how the system handles growth in specific circumstances.

### Describing the load

Choose load parameters, the dimensions of growth that we want our system to be able to handle.
- Requests per second
- Ratio of reads to writes

Twitter example:
- post tweet: avg 4.6k rps, max 12k rps
- view timeline: 300k rps


Handling 12k writes per second is easy. But 300k reads is more difficult. Twitter also has a guarantee to deliver tweets to followers within 5 seconds.
1. read-time joins: store tweets in a global table. when doing a timeline request, look up everyone you follow, grab tweets, and merge them.
    - this is slow when you have 300k read requests per second.
2. write-time fan out: maintain a timeline cache. When someone tweets, look up the followers and insert the tweet into every follower's mailbox. This makes reading timeline fast since the work is done already.
    - The downside is that posting a tweet takes more work.
    - On average, a tweet is delivered to 75 followers, so 4.6k tweets per second leads to 345k writes per second to the caches.
    - This wouldn't scale for celebrities with millions of followers.

Twitter takes a hybrid approach. Most users' use the write fan-out strategy but celebrity tweets are fetched separately and merged with the timelines when they are read.

### Measuring performance

- In batch processing systems (Hadoop), throughput (number of records per second) or the total time to process a dataset.
- In online systems, response time: time between client sending a request and receiving a response. Measured as a distribution of values, since there is randomness.
- Latency: the duration that a request is waiting to be handled.

Amazon optimizes for p99.9, because those customers will have the most data because they have made many purchases. (in the amazon SLO/SLA).

Tail latency amplification: in systems with multiple backend calls, a slow sub-request can slow down the entire end-user response.

### Approaches to cope with load
1. Vertical scaling
2. Horizontal scaling
    - elastic: automatically add computing resources when they detect a load increase
3. Shared-nothing: distributing load across multiple machines
    - Complex if data systems are stateful.
    - Usually recommended to vertically scale databases until high-availability requirements or scaling cost forces to make it distributed.

## Maintainability
Design principles for software systems:
1. Operatability: make it easy for operations to keep the systems running smoothly
2. Simplicity: make it easy for new engineers to understand the system
3. Evolvability: make it easier for engineers to make changes to the system in the future.
